# DocsKatArbitr

Веб-инструмент для скачивания всех документов из вкладки «Электронное дело» дела на kad.arbitr.ru и их конвертации в Markdown (для последующей работы с AI-агентом — PDF съедает гораздо больше токенов, чем текст).

## Запуск

Работает на **Python 3.14** — на дефолтном интерпретаторе проекта в PyCharm (`.venv/`), отдельный Python 3.11 больше не нужен (так было раньше из-за `undetected-chromedriver`, см. «Ключевые решения» про distutils-шим ниже).

```
.venv\Scripts\python.exe src\main.py
```

Из PyCharm можно просто нажать «Run» на `main.py` — тот же эффект. Можно и через `-m src.main` из корня проекта — оба способа работают. `src/main.py` сам добавляет корень проекта в `sys.path` и импортирует через абсолютный путь (`from src.modules.app import app`), а не относительный — иначе запуск напрямую (как делает кнопка «Run» в PyCharm, или голый `python src\main.py`) падал бы с `ImportError: attempted relative import with no known parent package`, потому что в этом случае Python добавляет в `sys.path` папку самого скрипта (`src/`), а не корень проекта, и не знает, что `main.py` — часть пакета.

Откроется Flask-сервер на `http://127.0.0.1:5000` (ссылка печатается в консоль при старте). Нужен установленный Google Chrome.

Зависимости перечислены в `requirements.txt` (в корне проекта): `flask`, `selenium`, `undetected-chromedriver`, `pypdf`, `openpyxl` (только для экспорта отчёта в Excel), плюс их транзитивные зависимости. Установка (если понадобится на новой машине/окружении):

```
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

## Архитектура

Весь исходный код лежит в пакете `src/` (`src/__init__.py` пустой, только чтобы сделать папку пакетом); корень проекта содержит только конфиг (`.gitignore`, `.idea/`, `CLAUDE.md`, `README.md`, `requirements.txt`). Внутри `src/` сам запускатор (`main.py`) и статические ресурсы (`templates/`) лежат на верхнем уровне пакета, а рабочая логика — в подпакете `src/modules/` (`src/modules/__init__.py` тоже пустой). Модули внутри `modules/` ссылаются друг на друга относительными импортами (`from . import scraper` и т.п.) — это безопасно, так как они всегда импортируются как часть пакета (через `main.py`, см. выше), а не запускаются как самостоятельные скрипты.

- **`src/main.py`** — тонкий запускатор Flask-приложения: добавляет корень проекта в `sys.path` (нужно для прямого запуска, см. «Запуск» выше), затем `from src.modules.app import app` + `app.run(...)`.
- **`src/modules/app.py`** — Flask-сервер: HTML-страница, фоновые задачи (в `threading.Thread`, не блокируют сервер), `state.json` (лежит в самой папке дела — см. ниже), `run_log.txt` (лог с таймстампами в выбранной папке сохранения). `templates/` лежит на уровень выше (`src/templates/`, рядом с `main.py`), не внутри `modules/` вместе со скриптами — поэтому `Flask(__name__, template_folder=...)` явно указывает туда, а не на дефолтный (относительно `src/modules/app.py`) путь.
- **`src/modules/scraper.py`** — вся Selenium-логика (навигация по сайту, скачивание PDF, подсчёт страниц, манифест, перенос пропавших документов).
- **`src/modules/converter.py`** — PDF → Markdown через `pypdf` (просто извлечение текстового слоя; документы кад.арбитр.ру не сканы, OCR не нужен).
- **`src/modules/report.py`** — строит табличные данные из `manifest.json` для `/report` и для выгрузки в `.xlsx` (`openpyxl`); никакой Selenium-логики, чистая работа с данными.
- **`src/templates/index.html`** — одна страница, двухколоночная адаптивная вёрстка, поллинг `/status` раз в 2 сек.
- **`src/templates/report.html`** — отдельная html-страница с таблицей по всем документам дела (открывается в новой вкладке кнопкой «Таблица по документам»), с фильтром по категории/поиском и ссылкой на Excel-выгрузку.

### Маршруты Flask (`src/modules/app.py`)

- `/` — страница.
- `/discover` — быстро узнать, сколько страниц в «Электронное дело» (один запрос, без обхода страниц). Если указана папка — на том же единственном открытии дела считывает со страницы карточки дела (это **до** переключения на вкладку «Электронное дело» — после переключения этот блок исчезает из DOM) номера дела из шапки, тему дела, дату начала и текущую длительность (сайт сам её считает), и участников по категориям (`scraper.get_case_info`), и сохраняет всё человекочитаемым текстом в `info.txt` (`scraper.write_case_info_file`), перезаписывая при каждой новой разведке.
- `/start` — полное скачивание (с опциональным диапазоном страниц через ползунки, опциональной конвертацией в MD). Если скачивание дошло до последней страницы (не ограничено узким диапазоном), в конце ещё раз заходит на страницу 1 — вдруг за время обхода туда подшили новый документ. Эта финальная перепроверка почти всегда находит уже скачанные документы (страница 1 уже была пройдена основным обходом) — такие «пропущено» в общую статистику `downloaded/skipped/failed` не идут, чтобы не раздувать счётчик повторным учётом одной и той же страницы; идут туда только по-настоящему новые находки (`downloaded`) и настоящие неудачи по ним (`failed`).
- `/actualize` — «Актуализировать»: один блок UI, одна функция (`scraper.run_actualize`). Обходит все страницы; для каждого документа сверка идёт **по `doc_id` через манифест** (`_verify_or_locate`), а не только по шаблону имени файла — если манифест говорит «скачан», но файла нет на диске, это отдельно логируется, не путается с «вообще не скачан». Если включена галочка «Докачать то, чего не хватает» — докачивает недостающее сразу в том же проходе, страница за страницей, и в конце тоже перепроверяет страницу 1. После полного обхода (независимо от галочки) переносит пропавшие документы в `vanished/` — см. ниже. Заменяет собой старые отдельные `/check` и `/download_missing` — они убраны, чтобы не было двух пересекающихся путей для одного и того же.
- `/convert` — только конвертация PDF→MD, без браузера вообще.
- `/report` — отчёт по всем документам из `manifest.json` (html-таблица, с фильтром и поиском), с явной колонкой `doc_id` и кликабельной ссылкой на PDF на сайте (для записей, у которых она известна — у доращенных из старых файлов записей ссылки нет, она никогда не была увидена). `/report/export.xlsx` — та же таблица в виде файла Excel, с тем же `doc_id` и рабочей гиперссылкой в ячейке (кнопка на странице отчёта и на главной странице).
- `/stop` — ставит `threading.Event`, который проверяется между документами/страницами и во время пауз бэкоффа.
- `/pick_folder` — открывает нативный диалог выбора папки Windows через `tkinter` (работает, потому что сервер и браузer на одной машине). После выбора сразу подгружает (или создаёт, если его там ещё нет) `state.json` **из выбранной папки** и отдаёт его фронтенду, чтобы поля формы (ссылка, темп, диапазон страниц, список пропусков) заполнились сами, если папка уже использовалась.
- `/folder_state` — то же самое, но для случая, когда папку не выбирают через диалог, а вписывают/вставляют вручную в поле — фронтенд дёргает этот роут при потере фокуса полем «Папка для сохранения».
- `/reset_state` — удаляет `state.json` из указанной папки (принимает `output_dir` в теле запроса) и сбрасывает связанные поля статуса.

## Ключевые решения и почему

- **Шим `distutils.version.LooseVersion` в начале `scraper.py`** — `undetected-chromedriver` (его `patcher.py`) делает `from distutils.version import LooseVersion` на уровне модуля; `distutils` убрали из стандартной библиотеки в Python 3.12, а проект теперь целится в 3.14 (дефолтный интерпретатор PyCharm, `.venv/`), так что без этого любой импорт `undetected_chromedriver` падал с `ModuleNotFoundError: No module named 'distutils'` ещё до старта браузера. Патчить саму библиотеку в `site-packages` не вариант — переустановка/обновление пакета это сотрёт. Вместо этого `scraper.py` сам регистрирует в `sys.modules` минимальную подмену `distutils`/`distutils.version` (класс с `.version` — разобранные по частям компоненты версии, и `.vstring` — исходная строка; это всё, что реально использует `patcher.py`) **до** `import undetected_chromedriver`, и только если настоящего `distutils` в принципе нет (`ModuleNotFoundError`) — на Python 3.11, где модуль ещё есть, это no-op и используется настоящий `distutils`.
- **`doc_id` — это не придуманный нами идентификатор, а GUID самого сайта.** Каждая ссылка на PDF в списке документов имеет вид `.../PdfDocument/<id дела>/<id документа>/<имя файла>.pdf` — `doc_id_and_name()` в `scraper.py` берёт именно второй кусок пути. Он виден в HTML страницы для каждого документа ещё до скачивания, и это внутренний первичный ключ документа в базе kad.arbitr.ru, а не хэш и не что-то, выведенное из названия — поэтому на него можно полагаться даже когда у двух разных документов, опубликованных в один день, совпадает отображаемое имя (так и есть в этом деле: несколько «Opredelenie.pdf» на одну дату, у каждого свой `doc_id`). Хэш файла для этой цели не подходит — его физически нет в HTML списка, узнать можно только скачав файл целиком, что убивает смысл проверки «уже скачано — пропускаем» без лишней нагрузки на сайт. В логе и в отчёте `doc_id` показывается явно (см. ниже), чтобы это было видно, а не спрятано внутри имени файла.
- **Имена файлов: читаемое имя + короткий суффикс `__xxxxxxxx.pdf`** (первые 8 символов `doc_id`) — у сайта часто несколько разных документов с одинаковым отображаемым именем (например, несколько `Opredelenie.pdf` за одну дату), так что какой-то привязанный к `doc_id` разделитель неизбежен, но полный 36-символьный UUID *в начале* каждого имени (как было раньше) делал всю папку нечитаемой. Суффикс *в конце*, и укороченный — коллизия по первым 8 символам UUID на выборке в тысячи документов практически невозможна. **Старые файлы не переименовываются** — `_existing_path()` в `scraper.py` узнаёт файл и по старой схеме (`{doc_id}_{имя}.pdf`), и по новой, так что обе схемы спокойно живут в одной папке.
- **`manifest.json`** (в корне папки результатов, рядом с `run_log.txt`) — отдельный файл-реестр: `doc_id → {title, filename, url, page_last_seen, downloaded_at, converted_at, last_verified_at, vanished_at}`. Это и есть «список того, что скачано/обработано и когда», отдельно от общего журнала `run_log.txt`. `last_verified_at` — дата, когда документ последний раз подтверждённо встретился на сайте (при скачивании или при актуализации) — это и есть «статус прохождения сверки» в отчёте, выражен просто датой, без отдельного поля-статуса. Заполняется и обновляется по ходу скачивания/докачки/конвертации (`scraper.load_manifest` / `save_manifest` / `record_converted`). При первом обращении к уже существующей папке результатов автоматически доращивает записи для файлов, которые там лежали до появления манифеста (по старой схеме имён), подставляя дату файла как `downloaded_at` с флагом `downloaded_at_estimated: true`, раз настоящий момент скачивания не известен.
- **`doc_id` в журнале** — каждая строка про документ (`[downloaded]`/`[skipped]`/`[failed]`/`[vanished]`/расхождение с манифестом) теперь начинается с короткого тега `#xxxxxxxx` (первые 8 символов `doc_id`, см. `scraper._tag`), чтобы было видно на глаз, что это реальный id с сайта, а не угадывание по имени файла — и сами записи-outcome теперь логирует `download_one()` один раз, а не каждый вызывающий код по-своему.
- **Сверка по `doc_id`, а не по совпадению имени файла** (`scraper._verify_or_locate`) — при актуализации (и при обычном скачивании тоже, раз оно теперь тоже передаёт манифест в `download_one`) каждый документ сайта сначала ищется в манифесте по `doc_id`; только если манифест вообще не знает про этот `doc_id`, идёт запасной вариант — поиск файла на диске по шаблону имени (`_existing_path`, нужен для доращивания старых папок). Если манифест говорит «скачан», но файла с записанным именем нет на диске — это отдельно логируется как расхождение (`[манифест] записан как скачанный, но файла нет на диске`) и документ перекачивается, а не тихо считается «новым».
- **`vanished/`** (папка рядом с `download/` и `md/`) — документы, которые раньше были скачаны, но при полном обходе всех страниц (`run_actualize`) больше не встретились на сайте ни на одной странице. `scraper.move_to_vanished` переносит туда и PDF, и соответствующий `.md` (если был), **не удаляя запись из `manifest.json`** — только помечает её `vanished_at`, чтобы осталась история «был — пропал». Если документ снова появится на сайте, `_record_seen`/`_record_downloaded` сами снимают `vanished_at`. Срабатывает только после полностью завершённого обхода всех страниц (не после прерванного Stop и не после скачивания только части страниц через `/start`) — иначе «не встретился» могло бы означать просто «вне диапазона», а не «пропал».
- **Каждый PDF скачивается в отдельной вкладке** (`window.open` + закрыть после) **а не в основной** — раньше скрипт делал `driver.get(pdf_url)` прямо в главной вкладке, что увозило её со страницы списка документов, и следующий клик по пагинации ломался (`NoSuchElementException`). Основная вкладка должна оставаться на странице «Электронное дело» всегда.
- **Скачивание через `Page.setDownloadBehavior` (CDP)**, не только через `prefs` — это единственный способ надёжно заставить Chrome скачивать PDF вместо открытия во встроенном просмотрщике.
- **`driver.get(pdf_url)` оборачивается в `try/except TimeoutException`** — переход на URL, который инициирует скачивание файла, не завершает «загрузку страницы» с точки зрения WebDriver, поэтому `page_load_timeout` специально короткий и исключение ожидаемо.
- **Детектор капчи по HTML-маркерам (`id="salto"`/`id="hash"`) был убран** — эти маркеры есть на **каждой** нормальной релей-странице перед скачиванием (сайт сам решает JS-пазл за 1-3 сек), не только на блокировке. Детектор давал ложные срабатывания и бесконечные зависания. Вместо этого — просто терпеливое ожидание файла на диске.
- **Флаги `--disable-backgrounding-occluded-windows`, `--disable-renderer-backgrounding`, `--disable-background-timer-throttling`** — без них Chrome тормозит JS-таймеры на странице, если окно не в фокусе, и сайт (AJAX-пагинация, релей-страница) не успевает отработать в срок.
- **`elapsed_seconds` в `/status`: свежий расчёт только пока задача реально выполняется**, иначе берётся последнее значение, записанное `log()` в `status["elapsed_seconds"]`. Раньше считали заново всегда (`time.monotonic() - _run_started_monotonic`) независимо от того, идёт ли задача — из-за этого после завершения счётчик продолжал расти до самого старта следующей задачи (используя всё более устаревающее время старта). Пока задача идёт, свежий расчёт всё равно нужен — иначе счётчик «замораживался» бы на долгих молчаливых участках без строк лога (например, обход 48 страниц при проверке). Округляется до целой секунды (было до 0.1с — точность, которая на статус-панели не нужна).
- **`state.json` живёт в самой папке дела, а не в корне проекта** (`app._state_path`/`_load_state`/`_save_state`/`_ensure_folder_state`) — так параметры дела (ссылку, темп, диапазон страниц, список страниц с пропусками) не нужно хранить где-то отдельно от самого дела: переставил/скопировал папку дела — переехали и настройки. Платим за это тем, что папку нужно выбирать/вводить каждый раз заново при открытии страницы (глобального «последнего состояния» больше нет) — это сознательный компромисс по просьбе пользователя. При старте страницы форма всегда пустая (дефолты); как только папка выбрана через диалог (`/pick_folder`) или введена руками (`/folder_state` по событию `change` на поле), её `state.json` подгружается (или создаётся с дефолтами, если его там ещё нет) и JS-функция `applyLoadedState()` заполняет остальные поля формы.
- **Статус-плашка в UI крупная и цветная** (`.status-banner` в `src/templates/index.html`), а не просто маленький бейдж — меняет цвет по фазе (idle/занято/готово/остановлено/ошибка) и под заголовком фазы всегда показывает одну строку человеческим языком про то, что происходит прямо сейчас (`buildActionLine()` в JS, собирается из тех же полей `/status`, что и остальная статистика).
- **Headless-режим скрыт из UI** (`display: none` в шаблоне, не удалён из кода) — не работает с этим сайтом, причина не выяснена. Можно вернуть, убрав `display: none`, если разберёмся.
- **Отдельный постоянный профиль Chrome для сохранения логина — пробовали и откатили** по запросу пользователя. Настоящая причина проблемы была не в профиле (профиль создавался нормально), а в том, что `open_electronic_case` слишком быстро сдавался и закрывал окно, если видел страницу блокировки/входа вместо карточки дела. Это исправлено отдельно (`_wait_for_case_page` — терпеливо ждёт до 20 минут, периодически перезагружая страницу, чтобы пользователь успел залогиниться вручную в открытом окне).

## Ограничение скорости (важно!)

У kad.arbitr.ru нет документированного API-лимита, но есть два разных вида блокировки:
1. **Мягкая** — список документов временно не грузится (0 страниц/0 документов), без сообщения, снимается сама за несколько минут.
2. **Жёсткая** — явная страница «Доступ ограничен... с вашего IP поступило необычно много запросов», требует авторизации на сайте. Один раз сработала, скорее всего, из-за того, что проверка раньше обходила все 48 страниц без единой паузы — это исправлено (теперь у обхода страниц всегда есть минимальный фиксированный темп, не завязанный на общий ползунок, даже если на странице не оказалось ни одного недостающего документа для докачки).

Текущие настройки (`scraper.py`):
- `MIN_RATE_PER_MIN = 1`, `MAX_RATE_PER_MIN = 10` — ползунок темпа скачивания/докачки.
- `CHECK_PAGE_DELAY = 1.0` — минимальный фиксированный темп перехода между страницами при актуализации (не настраивается ползунком; применяется всегда, независимо от того, идёт докачка на этой странице или нет — именно отсутствие паузы на «пустых» страницах было причиной прошлой жёсткой блокировки).
- `BLOCK_BACKOFF_SCHEDULE = [5, 10, 20]` минут — автоматические повторные попытки при мягкой блокировке.

Точный безопасный порог не известен — это рабочие оценки, не проверенные гарантии. Если снова поймаем жёсткую блокировку — разбираться по логам (`run_log.txt`), не гадать.

## Известные открытые вопросы

- Headless не работает (см. выше) — причина не выяснена.
- Точный порог жёсткой блокировки сайта не известен — текущие темпы (10/мин на скачивание, 1/сек на проверку) это рабочие оценки по итогам одного инцидента.
- **Дело живое**: в него до сих пор подшивают новые документы (видел даты почти на уровне "сегодня"). Из-за этого при обходе всех страниц (занимает от пары минут при актуализации до часов при полном скачивании) документ может сдвинуться со страницы на страницу и быть посчитан дважды — подсчёт в `run_actualize`/`run` считает уникальные `doc_id`, не сырую сумму по страницам, а финальная перепроверка страницы 1 (`_recheck_first_page`) ловит документы, подшитые уже после того, как обход до неё добрался. Если всё равно увидишь расхождение между "на сайте" и количеством файлов в `download/` — скорее всего, тоже эффект живых изменений в деле в процессе самого обхода, не баг.
- Если `download/` и `md/` расходятся по количеству — проверь на осиротевшие `.md` без PDF-первоисточника (бывает после ручного удаления файлов из `download/`, конвертация не чистит за собой).
- `manifest.json` подтягивается заново (с доращиванием недостающих записей) при каждом запуске любой задачи — если его вручную удалить, он просто пересоберётся из того, что лежит в `download/`/`md/`, но даты скачивания для уже существовавших на тот момент файлов снова станут «оценочными» (по mtime), а не точными.

## Структура папки с результатами (выбирается пользователем в UI)

```
<папка>/
  download/        — скачанные PDF: новые — {оригинальное_имя}__{короткий_id}.pdf, старые — {doc_id}_{оригинальное_имя}.pdf
  md/              — конвертированные .md, по одному на PDF
  vanished/        — PDF+MD документов, пропавших из карточки дела (из manifest.json не удаляются, только помечаются)
  manifest.json    — реестр doc_id -> {title, filename, url, page_last_seen, downloaded_at, converted_at, last_verified_at, vanished_at}
  run_log.txt       — журнал выполнения с таймстампами (накопительный, не перезаписывается)
  info.txt         — тема дела, номера из шапки, ссылка, дата начала и длительность на момент сбора, участники по категориям; пишется/перезаписывается при каждой «Разведке» (/discover), если указана папка
  state.json       — последние введённые в UI параметры для этого дела: ссылка, темп, диапазон страниц, список страниц с пропусками после последней актуализации. Создаётся/читается прямо отсюда при выборе этой папки в UI (/pick_folder, /folder_state) — не хранится отдельно от дела.
```
